# Cartograph v2.1.10

Cartograph v2.1.10 fixes the large native-index boundary reported in #117.
Resolver capacity failures are actionable, dense graphs are measured against
the correct working and final-output limits, PostgreSQL publication is batched,
and projects that intentionally need a larger in-memory generation can opt into
an explicit bounded ceiling.

## Large-project indexing and diagnostics

- Native pipeline capacity failures now retain a stable privacy-safe reason.
  Direct errors expose stage/reason pairs such as
  `resolve/generation_capacity_exceeded`; MCP admin jobs and auto-sync expose
  stable codes such as `resolve_generation_capacity_exceeded`. Extraction
  nesting and output limits have their own bounded parse reasons. No source,
  path, identifier, database URL, credential, SQL, or driver text is retained.
- Resolver unordered facts use a separately measured working allowance instead
  of the smaller final canonical-output ceiling. Deterministic reduction still
  proves that the published generation fits its configured output limit.
- Native reports include conservative resolve and canonical-validation
  high-water charges so operators can size an explicit large-project profile
  from evidence rather than retrying blindly.
- Project configuration accepts `maxGenerationBytes` from 1 byte through
  8 GiB. The default remains 1 GiB. Resolve and validation each receive a
  separately bounded working reservation of up to four times the configured
  canonical-output ceiling.

## Bounded publication and status

- Each canonical table is published through ordered PostgreSQL COPY statements
  bounded to 100,000 rows or 64 MiB of encoded rows. Every statement verifies
  its exact row count, and the complete generation remains in one atomic
  transaction.
- Successful COPY statements and subsequent preparation phases advance a
  monotonic progress observer. Long healthy publication is no longer mistaken
  for a stalled native stage, while the independent COPY and whole-operation
  deadlines still fail closed.
- Full-generation biomarker aggregation uses serial PostgreSQL planning and a
  five-second status deadline. If that optional lens is too expensive, status
  reports it as explicitly unavailable while preserving fresh generation,
  storage, numerical, graph, and query readiness.

## Extraction and digest contract

- Immediately invoked Go function literals and Python lambdas no longer retain
  their anonymous bodies as call-target names. Oversized Go selectors retain
  only their bounded stable field as dynamic-dispatch evidence; unstable
  composite targets are omitted.
- Per-file extraction separates a completed retained-output ceiling from its
  larger transient parser and fact-construction reservation, admitting dense
  generated schemas without weakening either bound.
- Migration 31 admits generation digest V12 for the bounded Go and Python
  call-target normalization. An unchanged V11 graph is therefore explicitly
  stale until a normal index publishes V12 evidence.

## Dependencies

- `ignore` is updated to 0.4.32.
- Compatible transitive updates include `aho-corasick` 1.1.5 and `ipnet`
  2.12.1. Every direct registry dependency is otherwise already at its current
  stable release, and the advisory, license, source, and duplicate-policy gates
  remain green.

## Upgrade notes

Use the resumable upgrade path so the installed binary, migration 31, current
generation, doctor checks, and owned host registrations reconcile in order:

```sh
cartograph upgrade --apply --project-path <PATH>
```

`maxGenerationBytes` is an explicit high-memory option, not an automatic scale
guess. Start with the 1 GiB default and raise it only after a typed capacity
result and a host-headroom review. Native parse, resolve, and reduce remain
bounded in-memory stages; COPY batching does not claim an arbitrary-size
spill-to-database pipeline.

Cartograph v2.1.10 remains native Rust and PostgreSQL-only. PostgreSQL 18,
ParadeDB `pg_search` 0.25.0, and pgvector 0.8.4 or newer remain external runtime
services. No SQLite runtime, fallback, importer, or dependency is included.
