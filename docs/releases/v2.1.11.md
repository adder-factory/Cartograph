# Cartograph v2.1.11

Cartograph v2.1.11 continues the large-project work behind #117 by replacing
the whole-generation native fact allocation with a generation-fenced,
PostgreSQL-backed streaming pipeline. It also removes two parser hot spots and
proves exact output on a 14,693-file, 171,015,058-byte public VS Code checkout.

## Bounded streaming for large generations

- `generationStorage` accepts `auto`, `memory`, or `postgres`. Automatic mode
  selects PostgreSQL spill at 10,000 supported files, 64 MiB of source, or when
  a conservative expansion estimate reaches the configured generation limit.
- The PostgreSQL path lazily forms each parse work item as the bounded scheduler
  admits it, with both a 64-file and 64 MiB source ceiling. One file above that
  byte ceiling remains one indivisible item. Its deadline begins at admission,
  so a large manifest cannot age later work in a prebuilt queue. Cacheable
  extraction payloads are written once to the immutable parse cache and staging
  rows retain a foreign-key-protected reference. A bounded inline payload is
  used only when a cache write is unavailable.
- Inline and cache-backed extraction rows share one logical batch identity and
  deterministic file/byte window. Live inline-to-cached and cached-to-inline
  retries prove that transient cache writes cannot create a replay conflict.
- Resolved files are validated and lazily encoded directly into 1 MiB PostgreSQL
  `COPY` transport chunks. Row, logical-byte, and retained-memory caps apply to
  every transaction; there is no generation-sized JSONB or text-encoded batch.
- Canonical reduction uses 64 deterministic UUID partitions per typed relation
  and commits four contiguous partitions at a time. Each transaction validates
  exact conflicts and cross-relations, inserts canonical rows, deletes its raw
  rows, and advances a durable retry cursor behind the generation lease.
- The exact canonical V13 digest streams from PostgreSQL in the same relation
  and key order as the memory reducer. The generation stays invisible until
  digest, counts, search relation, and ready-state checks all succeed, followed
  by the existing short atomic publication swap.
- Long streamed Resolve work reports exact completed pages, committed fact
  batches, derived passes, centrality work, and committed score batches. The
  supervisor no longer mistakes millions of advancing rows for a stalled outer
  work item. A genuine stall reports the same qualified, privacy-safe code in
  direct CLI, MCP admin, and auto-sync output, such as
  `resolve_progress_stalled`.

This is deliberately bounded streaming, not an unbounded-memory promise.
Per-file safety limits, compact project-wide resolver indexes, centrality
working state, configured spill row/byte quotas, database capacity, and stage
deadlines remain explicit fail-closed boundaries.

## Parser and reduction performance

- A spill parse worker now reuses one tree-sitter `NativeExtractor` per source
  language for its batch instead of rebuilding parser and query state for every
  file.
- Cooperative cancellation uses Tokio's atomic monotonic watch version in hot
  AST and clone-analysis probes. Parent cancellation, sibling failure,
  already-cancelled admission, channel closure, and exact deadlines preserve
  their previous semantics and regression coverage.
- Document conflict validation probes the typed identity index first and
  compares code, natural text, and metadata only when two raw rows claim the
  same document ID. A live hostile duplicate test proves that byte-different
  identities still fail closed.

On the public VS Code corpus, the optimized cold parse durably staged all
14,693 files in 23.04 seconds, versus roughly 2 minutes 50 seconds before these
parser fixes. The first resolved fact batch committed at 49.77 seconds after
the two bounded resolver-preparation passes. The final V13 cold request
published in 467.42 seconds versus 546.37 seconds for the successful cold V12
baseline. An earlier V12 warm-cache request completed in 415.57 seconds. Cache
states and digest contracts differ for the full-request figures and are
disclosed rather than presented as an isolated parser A/B.

The final candidate published V13 digest
`807bee88ee0a0c98b7127784243dcc2baae229e2e893b675c78505f36537f653`.
V12 and V13 intentionally have different digest contracts, while the measured
fact counts remain exact: 823,828 symbols, 1,541,789 edges, 2,724,385 reference
rows, and 823,828 search documents. The full reproducible evidence and quality
boundary are in the
[large public corpus streaming benchmark](../v2/benchmarks/LARGE-PUBLIC-CORPUS-STREAMING.md).

## Correctness and operations

- Spill tables, parse-cache references, state transitions, quotas, partition
  cursors, and canonical digest metadata are covered by append-only migrations
  32 through 35. Migration 36 admits generation digest V13 for corrected named
  TypeScript/JavaScript construction references; existing V12 generations
  become explicitly stale and reconcile through a normal index.
- Every spill transaction rechecks project, generation, sequence, and the
  database-clock lease immediately before commit with one joined query under
  its already-held mutation locks.
  Cancellation, deadline, database fault, conflicting identity, missing target,
  retry, and publication-parity paths retain live PostgreSQL coverage.
- Generation retention locks, counts, and audits every spill relation before a
  cascade, so a failed or abandoned large build cannot bypass cleanup work
  limits.
- Direct, MCP, auto-sync, and supervisor reports expose the selected storage
  mode and bounded spill progress without source, path, identifier, database
  URL, SQL, driver, or credential text.

## Upgrade notes

Use the resumable upgrade path so the installed binary, migrations 32 through
36, current generation, doctor checks, and owned host registrations reconcile
in order:

```sh
cartograph upgrade --apply --project-path <PATH>
```

The default `auto` storage policy requires no configuration change. Force
`generationStorage: "postgres"` when repeatable spill behavior is preferred,
or `"memory"` only when measured host headroom favors the faster in-memory
reducer. `maxSpillBytes` accounts logical payload rather than PostgreSQL heap,
index, WAL, or temporary-space amplification; inspect database capacity before
raising it.

Cartograph v2.1.11 remains native Rust and PostgreSQL-only. PostgreSQL 18,
ParadeDB `pg_search` 0.25.0, and pgvector 0.8.4 or newer remain external runtime
services. No SQLite runtime, fallback, importer, or dependency is included.
