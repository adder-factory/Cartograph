# Cartograph v2.2.0

Cartograph v2.2.0 makes the code-health lens usable on a real graph, stops one
ordinary source construct from costing a whole index, adds a flexible and
self-reporting exclusion mechanism, and indexes WGSL and Metal shaders as
first-class sources. It closes issues #118, #119, #120, and #121.

## Structural findings are computed once and stored

The readiness probe in `cartograph_status` evaluated the complete detector
cascade under a five-second deadline. On a 38.8k-symbol graph that statement
took about eight seconds, so status reported `state: unavailable`,
`reason: timeout` while the same statement succeeded elsewhere under the
thirty-second insight deadline.

Two independent defects were at work.

The detector CTEs fenced every relation by joining an opaque `current` CTE.
PostgreSQL has no statistics for a CTE scan, so it chose a nested loop between
symbols and the outgoing-dependency relation and discarded 165,805,115 rows
through the join filter. The generation is now resolved once and bound as a
parameter, which lets PostgreSQL build a custom plan against the real value.

The complete relation is then computed once per exact input fingerprint and
stored generation-fenced (schema version 37, `structural_finding_runs` and
`structural_findings`). The fingerprint covers the current generation, the
superseded generation the growth detector compares against, imported coverage,
materialised similarity scores and per-build provenance, the calendar day that
bounds the `recently_grew` window, and a digest of the detector contract
compiled into the binary — so a detector-SQL change can never keep serving
findings the shipped rules no longer produce.

On a 39k-symbol corpus the first computation completes in 27 seconds where it
previously did not complete at all, and the stored relation then answers in
half a second. `cartograph_status` only reads stored rows and reports an
explicit `state: pending`, `reason: not_computed` before the first computation —
never an empty finding set.

## One construct no longer costs the whole index

A method chain of 64 calls synthesised a reference name past the 4096-byte
canonical bound, and a `pub use` group naming 56 constants synthesised a
qualified name past the 2048-byte bound. Both discarded the entire generation,
and the second reported only a generic `reduce_failed` with no reason, no file,
and no symbol.

An extractor synthesises names from source structure, so some construct will
always reach some bound. An over-long name is now shortened deterministically —
a prefix cut on a character boundary, a `~` marker, and a digest of the exact
original name — and the file carries a `canonical_name_truncated` diagnostic so
a shortened identity is never mistaken for the complete one. Names within their
bound are untouched, so no corpus that indexes today changes identity or digest.

A bounded field with no safe shortening still fails canonical reduction, but the
failure now names the exact rejected storage field as
`canonical_field_rejected(<field>)`.

## Flexible, reported source exclusion

There are three ways to exclude a path, and all of them apply to `sync-if-dirty`
and the managed Git hooks:

- the `exclude` array in `.cartograph/config.json`, which is durable and shared;
- `cartograph index --exclude <GLOB>`, repeatable and scoped to one run;
- a `.cartographignore` carrying patterns, honored with gitignore semantics.

Both `exclude` forms accept a `!` prefix that re-includes a path an earlier
exclusion matched. Directory pruning is disabled while any negation is
configured, because a pruned directory is never descended into and the
re-include could never fire. Pattern `.cartographignore` files are applied on
admission as well as in the walker, so git-tracked collection cannot silently
keep a file the walker skipped. An empty `.cartographignore` keeps its original
meaning of dropping its whole tree.

Exclusions report themselves: native index metrics carry `excluded_paths` and
`excluded_trees`. A pruned tree is deliberately not expanded into a file count,
because walking it to produce one would defeat the pruning.

## WGSL and Metal shaders

Shaders are where a large share of a renderer's logic lives. WGSL gets its own
extraction slice covering functions, structs and members, module-scope
bindings, type aliases, entry points typed by pipeline stage, intra-file calls
and declared-type edges, and `naga_oil` `#define_import_path` and
`#import module::path`. A `@vertex`, `@fragment`, or `@compute` function is a
public boundary reachable from host code, so `entry-points` now reports it.
Metal reuses the existing C-family slice, since its shading language is
C++-based. The registry now recognises 128 native source-language modes.

Two boundaries are explicit rather than silently absent. The pinned grammar
accepts `#import module::path` but not the quoted-file form, so a quoted import
yields a recoverable diagnostic and a partial parse. And `@group`/`@binding`
indices are not spelled into a signature, because a literal-bearing signature is
rejected before persistence; a binding carries its declared type as a typed
reference edge instead. Correlating those indices with a host-side layout entry
is not implemented.

## Code health

The repository's own code-health findings are now zero at every severity, down
from seven errors, thirty-two warnings, and thirty-nine info findings. The work
was structural rather than cosmetic. Five per-relation digest functions that
differed only by relation name, columns, and order key are now described rather
than copied. Six payload encoders became one generic pass over a trait. Per-stage
code lookups became tables, so a new pipeline stage cannot be added to one
lookup and forgotten in another. The eleven-family walker dispatch became a
`FamilySlice` table pairing each family's declaration and usage entry points,
which is the pairing whose absence would let a new family's files look
successfully empty. Canonicalisation and row admission moved off the spill type
into the storage steps they are. Repeated argument groups became named types,
and fifteen methods stopped taking a schema their receiver already owned.

Relation order and encoded columns feed the generation content digest, so the
locked native-corpus gate pins that none of this changed behaviour.

## Upgrade

`cartograph upgrade --apply` applies schema migration 37. The first
`cartograph_status` after upgrading reports `biomarkers: pending` until the
first `cartograph biomarkers` call computes the relation.
